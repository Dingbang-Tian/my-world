## 本阶段问题与调用链

现有启动模块直接依赖 `my-world-ai`，尚无公共 Agent 与代码生成应用的模块边界。本阶段把 Maven 依赖和 Spring 装配接起来，为后续 API 留出正确位置；没有实现模型消息或工具循环。

```text
MyWorldApplication（Spring Boot 扫描）
  → AiApplicationConfiguration（AI 应用）
  → AgentModuleConfiguration（公共 Agent）
  → SpringAiConfiguration（现有模型接入/普通对话）
  → AiChatService（现有文本对话服务）
```

运行前预测：test profile 中的 Spring 上下文应包含三个配置类及现有 `AiChatService`；假模型在启动时不被调用；`mvn package` 应产出两个普通 JAR 和一个可执行启动 JAR。实测结果与预测一致。

## 实现位置

- 根 `pom.xml` 加入 `my-world-ai-agent`、`my-world-ai-app`，按依赖顺序放在 `my-world-ai` 与 `my-world-app` 之间。
- 当时的初版 `my-world-ai-agent/pom.xml` 依赖 `my-world-ai`；后续为分离 Spring AI 与自研框架，已调整为依赖 `my-world-ai-framework`，`AgentModuleConfiguration` 不再导入 `SpringAiConfiguration`。
- `my-world-ai-app/pom.xml` 依赖 `my-world-ai-agent`；`AiApplicationConfiguration` 导入 Agent 配置。
- `my-world-app/pom.xml` 增加对 `my-world-ai-app` 的依赖；原有 `my-world-ai` 与 `my-world-common` 直接依赖保留。
- `ModuleAssemblySmokeTest` 以 test profile 启动 `MyWorldApplication`，在独立测试配置中提供一个被调用即报错的 `ChatModel`，验证三个配置类和 `AiChatService` 均存在。`s01-smoke-test.yml` 使用测试用占位 API Key，覆盖原应用配置中的加密默认值；没有真实凭据或网络请求。

本阶段新增两个配置类只负责装配，没有提前建立 S02–S06 的空 API。参考 `AgentClient.createSession()` 显示参考项目把模型、工具、技能放在同一客户端内；当前项目按图纸先以 Maven 和 Spring 配置明确依赖方向，具体 Agent 接口以后再引入。没有复制参考 Java 源码。参考 POM 是单模块、Java 17、GPL v3；目标沿用自己的父 POM 和 Java 21。

## 设计取舍与边界

取舍：用 `@Import` 明确 `ai-app → agent → ai` 的配置链，使外部项目导入 AI 应用配置时也能得到下层配置；`SpringAiConfiguration` 仍由 `my-world.ai.enabled` 控制。当前仍只有普通文本对话服务，Agent SDK、工具和代码生成留在各自阶段。没有引入新的凭据处理或模型调用逻辑。

S02 将新增协议中立的消息和单次模型请求契约，并用 scripted 假模型检验消息与完整结果。

## 用户回答与补充讲解（2026/10/01）

1. 用户回答“防止进入循环依赖”。这点正确：`ai-app` 已经依赖 `ai-agent`，反向依赖会形成 Maven 环。更根本的边界是公共 Agent 应服务不同业务应用；如果它导入 `codegen` 文件工具，其他应用也会被迫依赖代码生成实现。
2. 用户表示不清楚普通 JAR 与可执行 JAR 的区别。普通 JAR 把类放在标准 classpath 路径，其他 Maven 模块可直接依赖；Spring Boot 可执行 JAR 带启动器，并把业务类放在 `BOOT-INF/classes`、依赖放在 `BOOT-INF/lib`。新增库模块没有独立 `main` 入口，是供启动模块及其他业务模块依赖的库；只有 `my-world-app` 负责启动。
3. 用户询问装配测试在哪里。它位于 `my-world-app/src/test/java/com/dingbang/myworld/ModuleAssemblySmokeTest.java`：`loadsModuleChainAndExistingChatService()` 启动 Spring 上下文并断言三个配置类和 `AiChatService` 存在；`testChatClientBuilder()` 提供被调用即报错的假模型。这个测试证明装配成功、启动时未调用模型；它没有发送 Agent 请求，也没有验证模型提出工具调用后的执行、结果记录和续问。

### 后续边界调整（2026/10/01）

用户指出 Spring AI 与自研框架需要可独立引入。于是新增 `my-world-ai-framework` 普通 JAR，承载协议中立的 `ModelGateway`、消息和事件契约；`my-world-ai` 保留 Spring AI `ChatClient`、配置和普通对话适配器。自研 Agent 只依赖 framework，Spring AI 不再通过 Agent 配置传递进入自研框架。

### 第二次回答（2026/10/01）

用户说“启动 JAR 是在启动时使用，普通 JAR 是在运行时”。这里把**用途**误认为**使用时机**：普通 JAR 的类在编译时参与类型检查，在程序运行时也会被加载；可执行 JAR 提供 `main` 入口并打包启动器，启动之后也持续参与运行。区别是库与启动程序的角色和打包结构，不是只在某一个时刻使用。装配测试的验证边界仍待用户回答。

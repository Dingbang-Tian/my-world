# S10–S11：代码生成应用与九个文件工具

## 调用链

`CodegenConfiguration` 仅在 `my-world.codegen.enabled=true` 时绑定绝对工作目录、modelId 与写权限。`CodegenFactory` 创建只属于 `codegen` 应用的 `AgentDefinition`、文件技能和工具注册表。默认只注册五个只读工具；`write-enabled=true` 才同时注册四个写工具。`CodegenService` 将可信 ownerId 和固定应用/Agent 身份交给公共 `AgentService`；公共 Agent 循环无需修改。技能说明按实际授权生成，关闭写权限时 SYSTEM 不宣称可写。模型即使伪造关闭的 `create_file` 调用，`ToolExecutor` 仍返回 `TOOL_NOT_FOUND`。

启用示例：

```yaml
my-world:
  codegen:
    enabled: true
    model-id: codegen-main
    workspace: /absolute/path/to/workspace
    write-enabled: false
```

假模型轨迹：用户要求理解目录 → 模型收到五个工具描述 → `list_directory_tree` 读取临时目录 → 第二轮模型请求包含同 callId 的工具结果 → 助手回答。另一个假模型轨迹在启用写权限时创建 `result.txt`，结果与 `FileArtifact` 都记录该文件。

## 文件边界与行为

`WorkspacePolicy` 使用启动时的工作目录真实路径，只接受相对路径；标准化后检查根目录范围，并拒绝路径中任一已存在的符号链接。每个文件工具都复用该策略；写工具在创建父目录后再次检查。目录树和搜索不跟随符号链接。此策略约束工具路径，不是操作系统级沙箱；S12 的命令工具需单独处理权限。

五个只读工具：目录树限制深度 0–20；文件读取显示从 1 开始的行号、总行数和完整字节 SHA-256；文件名及内容搜索支持 1–20 个关键词，内容搜索可选前后 0–20 行上下文。UTF-8 严格解码；单文件读取最多 1 MiB，搜索最多检查 1000 个文件，单次结果最多 16000 字符并标记截断。空目录、无匹配内容给出明确文本。`maxDepth`、`patterns` 等参考参数名可用。

四个写工具：`create_file` 使用 CREATE_NEW，允许创建父目录，拒绝覆盖；`edit_file` 要求从读取结果得到的当前 SHA-256，可按唯一旧文本或指定行范围 replace，也可在行前 insert 或 append，保留原文的换行符；`move_file` 校验源版本与目标空闲，源/目标两端都走路径策略；`delete_file` 仅删除已存在普通文件，要求当前版本，重复删除报错。单文件写入最多 1 MiB。写成功后返回摘要，并按 runId 保存内存中的 `FileArtifact`。版本冲突时拒绝操作且提示重新读取。哈希在操作前再次校验，仍不承诺跨进程写入或崩溃后的事务原子性；不确定副作用恢复留 S19。

对照 Agent4J 九个 Tool/Param 与 FileSystemSkill：保留工具名称和主要模式；目标额外拒绝意外覆盖、目录删除、越界及符号链接路径，并要求修改前版本。参考 `EditFileTool` 的逐行 `Files.write` 会改写换行风格；目标在原始字符串上计算行偏移以保留 CRLF/LF。未复制参考源码。


## 理解问题

1. 哪些逻辑属于 codegen，哪些属于公共 Agent？为什么增加文件工具不需要修改 `DefaultAgentRun`？
2. 写工具默认关闭时，为什么既要从模型描述中移除，也要在 `ToolExecutor` 的授权注册表中拒绝？
3. 为什么规范化相对路径后还要检查真实路径和符号链接？
4. 为什么 `view_file` 返回 SHA-256 后，`edit_file` 仍要在真正写入前再次验证？
5. 为什么助手文字说“已创建文件”不能替代工具成功结果和产物记录？
